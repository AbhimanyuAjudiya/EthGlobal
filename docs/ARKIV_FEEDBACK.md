# Arkiv feedback: what we built on Arkiv, what we measured, what was awkward

Recharge keeps every entitlement, gift escrow, receipt, challenge nonce and agent policy as an Arkiv entity on the
**rabdi testnet (chain 7794095)** through `@arkiv-network/sdk@1.0.1`. Expiry is the product: a bundle is valid exactly as
long as its entity lives. There is no Postgres and no cron job.

- Schema file: [`docs/arkiv.schema.json`](arkiv.schema.json), generated by `pnpm schema:gen` from
  `packages/protocol/src/schemas/entities.ts`. CI fails on drift (`pnpm schema:check`).
- Code: `packages/adapters/src/live/arkiv-ledger.ts` (the mapping rules) and `packages/adapters/src/live/arkiv-sdk.ts`
  (the one file that imports the SDK). The annotations and queries live in `packages/octroi/src/store/*`.
- Swarm: [`docs/SWARM.md`](SWARM.md).

## 1. What we built on Arkiv

| Entity type (`recharge.<type>.v1`) | Logical key (`logicalKey` attribute) | Indexed attributes | `expiresIn` | Read by |
|---|---|---|---|---|
| `entitlement` | `hk:` + sha256 of the capability key (the key itself never reaches the ledger, A-34) | `type, logicalKey, kind, status, tier, campaignId?, iccidHash?, expiresAt` | the plan validity (`validityDays × 86 400`, 7 d by default), reset on top-up | **R1** every `/esim/*` and `/me/:key`; **R2** the agent tick; the sponsor "expiring" table |
| `campaign` | `camp:<id>` | `type, logicalKey, sponsor, expiresAt` | until the campaign's `expiresAt` | `/plans`, `/claim` |
| `gift` | `gift:<giftId>` | `type, logicalKey, kind, state, namehash?, pinKey, serial, campaignId?, expiresAt = claimBy` | `claimBy − now` (7 d claim window) | **R3** gift claim by namehash and card redeem by PIN key; the reclaim expects its **absence** |
| `nonce` | `nonce:<nonce>` | `type, logicalKey, nonce` | 300 s (`NONCE_TTL_S`, ≥ the 120-s challenge plus skew and drift, A-37) | challenge consume (replay guard), written create-if-absent |
| `receipt` | `rcpt:<network>:<tx>` or `rcpt:ledger:<uuid>` | `type, logicalKey, receiptKind, entitlementKeyHash, campaignId?, day` | `RECEIPT_TTL_S` (claim window + reclaim window + 1 d = 38 d, A-36) | `/me/:key/receipts`, sponsor claims, the agent's spend today, gift reclaim |
| `agentpolicy` | `policy:<entitlementKey>` | `type, logicalKey, owner` | 30 d | the agent tick, `/agent/policy/:key` |
| `claim` | `claim:<opaque digest>` | `type, logicalKey, expiresAt` | until its `expiresAt` | one-claim / one-serve locks, written create-if-absent (A-33) |

**Division of truth.** The reseller is the truth for *usage*, Arkiv is the truth for *entitlement*, and the signed
reseller webhook reconciles the two (it patches `mbUsed`/`usageAsOf` on the entity, and `/me` drops its cache).

Every payload is world-readable. None carries a nullifier, an ICCID in clear, an LPA (clear or sealed), a PIN, a
private key or a capability key. The red team greps the ledger dump for those after every e2e run
(`security/redteam/tools/forbidden-patterns.txt`).

**Block time.** rabdi is nominally 2 s. Measured: **TBD by human (Integrations, Wed 14:00)**, as Δblock over Δwall-clock
across the pre-deploy. Set `ARKIV_BLOCK_TIME_MS` to the measurement.

**Expiry rounding (T-35, A-24).** `expiresIn` seconds become `ExpirationTime.fromSeconds(...)`, which counts **whole
2-s blocks, rounded up**. A 90-s entity therefore lives 90 s (45 blocks), while a 91-s entity lives 92 s. The maximum
lifetime is 7 884 000 blocks (182.5 days). `ArkivLedger` logs `impliedDriftSec` whenever the block-time assumption and
the requested seconds disagree. To make expiry exact to the millisecond on reads anyway, every entity also carries a
numeric `expiresAt` attribute, and the stores treat an entity as dead at `min(ledger expiry, expiresAt)`.

## 5. SDK feedback

These are the points we hit while designing and testing against the SDK's types and the recorded call shapes in
`MODE=local`. The humans add the live ones on Wednesday and in the window.

1. **`key` is a reserved word in the query language.** An attribute named `key` fails the SDK's schema validation, so
   our logical key is stored as `logicalKey` (`TO_ATTRIBUTE` in `arkiv-ledger.ts`, decision AL-2). The error message did
   not say "reserved"; we found it by running the validator. Suggestion: list the reserved words in the docs and name
   them in the error.
2. **Attribute typing is per value, not per schema.** Indexed values are `str` or `u64`, so we keep a fixed set of
   numeric attributes (`expiresAt`, `day`) and stringify everything else. A typed per-entity-type attribute schema in
   the SDK (with `defineSchema`) would catch a numeric attribute written as a string at compile time, rather than as a
   query that silently matches nothing.
3. **`$creator` versus `$owner`.** Ownership can be transferred, but the creator cannot. Every one of our reads filters
   `eq('$creator', writer)` (T-79), so that a third party writing look-alike entities with our attribute names cannot
   poison a read. This is the most important line in our adapter, and it is easy to get wrong. Suggestion: make it a
   first-class "my entities" query option, documented as the safe default.
4. **Update semantics and expiry.** An update with a *shorter* `expiresIn` cannot move the ledger expiry earlier (AL-3).
   We keep the longer ledger lifetime, log it, and end the entity on time through the `expiresAt` attribute. A
   documented "expire now" or "shorten" operation would remove the need for that second clock.
5. **No compare-and-swap or create-if-absent.** Our red team found read-modify-write races in the stores (RT-O-03, -05,
   -06: two concurrent claims, a lost usage patch, a double create of one logical key). The fix in the `Ledger` port
   (A-32) adds `ifAbsent` puts and `ifVersion` updates. On Arkiv these need a primitive we could not find in 1.0.1.
   Until then they are enforced by one writer process. Native conditional writes (create-if-absent by attribute, update
   if the entity version matches) would make Arkiv a safe lock and idempotency store.
6. **Expiry visibility.** An expired entity simply disappears from `getEntity` and `select`. Telling "expired" apart
   from "never existed" needs our own memory (the API keeps the last-seen `expiresAt` to answer 410 instead of 404). A
   tombstone read, or `getEntity` returning `{ expiredAt }` for a recently expired key, would let clients show "your
   plan ended at 14:02" honestly.
7. **Pagination.** We page by key (`gt('$key', afterKey)`, `asc('$key')`, 100 per page, at most 1 000 rows per query).
   A cursor in the response would remove the need to re-sort client-side.
8. **Payload as bytes.** The payload is a `bytes` attribute (UTF-8 JSON, ≤ 128 KiB). Content-type metadata on the
   entity would let explorers render JSON payloads directly.
9. **A bare bigint is a u256, not a u64 (hit live, 2026-11-05, RT-A-15).** Our first real write on rabdi failed inside
   the SDK, before any transaction: `SchemaMismatchError: Column "createdAtMs": a u64 column, but the value is a u256.
   Write u64(...) around the value`. The schema said `u64()`, the value was a JavaScript `bigint`, and `toValue` picks
   the widest integer type for an untagged bigint. The message is excellent — it names the column and the fix — but
   nothing in the `defineSchema` typing forced the tag at compile time, and `MODE=local` never runs the SDK's validator,
   so it surfaced only on the live chain. Suggestion: when a schema is given, coerce a bare bigint to the column's own
   integer type (the column already knows it is u64), or make `CreateEntityValues<S>` reject a bare bigint for a u64
   column so `tsc` catches it. We now tag every value at the boundary (`toSdkValues`).
