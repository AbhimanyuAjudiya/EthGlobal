**The one sentence we defend:** *prove you're human and a sponsor pays for your first 300 MB of Mumbai data; after that you — or your agent — pay per 100 MB over x402, every bundle is an Arkiv entity that expires by itself, and anyone can gift data to an ENS name.* Every clause is a trust decision with money behind it: a sponsor's USDC is released by our attestor key on the strength of a World ID proof; an eSIM activation code (a bearer secret worth real money) is handed to whoever paid; an agent holding a user's USDC buys on its own; a gift is claimable by whoever controls a name. Those four releases are what this document is about.

## 0. Conventions

- **Severity.** *Critical* = loses sponsor or user funds, lets an unverified party into the sponsor-funded lane at scale, or leaks activation codes; *High* = breaks a core claim of the product (one-human-one-claim, unlinkability, expiry-by-protocol, agent caps) or the stage demo; *Med* = contained loss, degraded trust, or recoverable outage; *Low* = nuisance or hygiene.
- **Likelihood** (given a hostile crypto-twitter audience on launch day, a $0.50 World-ID resale market, and a team that touches real chains for the first time on Wednesday): *H* / *M* / *L*.
- **STRIDE:** S spoofing · T tampering · R repudiation · I information disclosure · D denial of service · E elevation of privilege.
- **"Control that must exist in the code"** is a build requirement. A builder who cannot implement it as written must raise it in `security/redteam/findings/` as an *accepted-risk* candidate, not silently drop it.
- **Mode.** Everything below is attackable in `MODE=local` (Anvil 31337, `MockUSDC3009`, in-memory/fixture adapters) unless marked **live-only**, which the human team runs at the Wednesday pre-deploy or the Friday drill.
- Units: USDC amounts are **6-decimal base units** (`$0.50 = 500_000`); timestamps are **seconds** on-chain and in EIP-3009 authorizations, **milliseconds** in `LedgerEntity.expiresAt` / `EsimUsage.asOf`; MB are integers.

## 3. Trust boundaries

```
 TB-1  user device / PWA  ──TLS──▶  services/api (Hono)          untrusted client; airport Wi-Fi (ACT-11)
 TB-2  api  ──HTTPS──▶  World cloud verifier (POST developer.world.org/api/v4/verify/{rp_id}; IDKit 4 result forwarded unchanged;
                        the API also signs rp_context with WORLD_RP_SIGNING_KEY)   trusted oracle for personhood — only for environment 'production' (T-80)
 TB-3  api  ──HTTPS──▶  x402 facilitator (RemoteFacilitator) | in-process SelfRunFacilitator (+ relayer key)
 TB-4  api  ◀─HTTPS─▶  eSIM reseller (EsimAccessReseller primary; MegaEsimReseller fixture-only stub, A-28): orders out with RT-* HMAC headers
                        (key = accessCode); LPA in the `ac` field of /esim/query; webhooks in UNSIGNED (URL token + sender IPs + re-read, A-27)
 TB-5  api  ──SDK──▶  Arkiv (ArkivLedger, @arkiv-network/sdk 1.0.1, rabdi 7794095)   PUBLIC: every payload and annotation is world-readable,
                        and anyone can WRITE look-alike entities — reads must filter on $creator == our writer (T-79)
 TB-6  api (attestor key)  ──JSON-RPC──▶  DataDrop.sol on Hedera EVM 296  (Anvil 31337 local)   PUBLIC
 TB-7  services/agent (own wallet)  ──HTTP──▶  api   the agent is just another paying client
 TB-8  sponsor wallet  ──tx──▶  DataDrop.createCampaign / pause / refund   sponsor controls its own funds only
 TB-9  operator laptop / VPS / CI  ↔  secrets (.env), deploy artefacts (deploy/addresses.<slug>.json)
 TB-10 LLM (notification phrasing only)  ◀──  strings from ledger payloads   untrusted text in, text out, never a decision
```

Keys are **separated by boundary**: attestor (TB-6), relayer (TB-3), reseller API key + webhook secrets (TB-4), HMAC quota secret (inside the API), HCS submit key, agent wallet (TB-7), sponsor wallet (TB-8), owner of `DataDrop` (cold, on-site). A compromise of one boundary must not hand over another (T-01, T-10, T-29).

## 4. Data flows and what crosses each boundary

Names are those of `docs/INTERFACES.md` (§1 `@ethglobal/protocol`, §5 `@ethglobal/octroi`, §7 the HTTP contract) and `docs/ARCHITECTURE.md` §2. **R1–R3** are the three load-bearing Arkiv reads. Nothing is persisted on a 402.

**F1 — free welcome bundle.** PWA generates an X25519 session keypair (memory only) → `POST /challenge { audience:'recharge', path:'/claim', sessionPubKey }` → `octroi.challenge(audience, path, sessionPubKey, now, OCTROI_SECRET)` mints `{ nonce = random16 ‖ HMAC(secret, random16‖audience‖path‖exp‖sessionPubKey)[0..16], exp = now+120 s, signal = keccak256(nonce ‖ 'recharge') }` — **no ledger write** (D-3) → `POST /world/rp-context` (backend-signed `rp_context`, `signRequest(WORLD_RP_SIGNING_KEY, action, ttl 300)`, no ledger write, A-25) → IDKit 4 (`app_id`, action `recharge-welcome`, `rp_context`, legacy preset with `signal`) → `POST /claim { proof = IDKit result unchanged, campaignId, challenge, sessionPubKey }` (5/min/IP, zod, `octroi()`) → `decide()` **in this order**: request validity → `CampaignStore.get` (R0) + on-chain `counters` (`campaigns(id)`, `claimsInHour`, `claimed`) say live/budget/cap → admission slot (per-campaign queue, T-46) → `consumeChallenge` (MAC + session key + exp; in-memory set synchronously; `NonceStore.consume` writes `nonce:<nonce>` `expiresIn 120`; `'unavailable'` ⇒ deny) → `personhood.verify(proof, { action, signal })` (`WorldCloudPersonhood`: `POST /api/v4/verify/{rp_id}`; asserts `success`, `action`, `environment === 'production'` in live, every `signal_hash == hashToField(signal)`; nullifier decimal → hex32) → `tier = tierFromLevel(result.level)` (level from the **response** identifier) → `mb = sizeBundle(campaign, tier)` (0 ⇒ `payment-required`) → `quotaKey`, `campaignClaimKey = HMAC(auditKey_c, nullifier)`, `onchainClaimKey = keccak256(id ‖ cck)` → replay (`existingEntitlement` or `counters.claimed`) ⇒ `deny: replay` → `serve-free`. API: `DataDrop.claim(id, claimKey)` from the single attestor sender queue → `fulfil()`: `reseller.order(planId, { idempotencyKey: claimKey })` → clear LPA exists only here → `sealLpa(lpa, sessionPubKey, lpaAad(challenge.nonce, key))` → `blobs.put` → `EntitlementStore.create({ key: keys.entitlementFree(quotaKey), kind:'free', status:'ready', …, sealedRef, expiresAt })` → `ReceiptStore.add('claim')` → HCS `claim`. Order failure ⇒ `FallbackReseller` (inventory) ⇒ else `status:'pending-profile'`, **202**, retried by `/me/:key` with the same idempotency key (D-6, T-25). Response `entitledResponseSchema` carries `sealedLpa` **once**.
Secrets crossing: proof + nullifier (TB-1→API→TB-2); attestor signature (TB-6); clear LPA (TB-4→API, stops in `fulfil()`); sealed LPA (API→TB-1, once).

**F2 — paid lane (`GET /esim/provision?mb=`, `GET /esim/topup?key=&mb=`).** `fetchWithPayment` → 402 with `accepts[] = buildAccepts(deps, mb)` (`X402_NETWORKS`; local `eip155:31337` MockUSDC with `extra {name:"USD Coin",version:"2"}`; demo `eip155:84532` USDC `0x036C…CF7e` with `extra {name:"USDC",version:"2"}` + `hedera:testnet` HTS `0.0.429274` with `extra.feePayer` and `maxTimeoutSeconds ≤ 180`; the only amount field is `accepts[].amount`, A-18/A-20/A-21) → `PaymentSigner.choose()` → `Authorization3009 { from, to: payTo, value: priceUsd6(mb), validAfter 0, validBefore now+300, nonce }` where **`nonce = sessionNonce(sessionPubKey) = keccak256(sessionPubKey)` on LPA-delivering routes** (`/esim/provision`, header `X-Session-Pubkey`) and `random32` on plain top-ups → `PAYMENT-SIGNATURE` → `decide()`: `payload.accepted` deep-equals one `accepts[]` entry incl. exact amount → session-nonce binding when `requireSessionKey` → per-ICCID daily cap → `payments.verify` → `payments.settle` (`X402_FACILITATOR=self`: `SelfRunFacilitator` relays `transferWithAuthorization` and waits for the receipt; `remote`: `RemoteFacilitator`; Hedera scheme: `{ transaction: base64 partially-signed TransferTransaction }` with `transactionId.accountId == extra.feePayer`, co-signed and submitted by the facilitator; settlement id `0.0.x@s.n` in `transaction`) → `serve-paid` → `reseller.topUp(iccid, mb, { idempotencyKey: nonce })` / `order` → `EntitlementStore.patch` (`ledger.update` with a new `expiresIn`) → receipt → HCS `settle` → 200/201 + `PAYMENT-RESPONSE`.
Secrets crossing: a signed authorization anyone may submit (T-15); sealed LPA once (provision).

**F3 — gift, card, reclaim.** `POST /gift { name, mb, message? }` → `names.resolve(normalize(name))` **before** any 402 (404 `name_unresolved`) → F2 dance → `giftId = keccak(payer ‖ nonce)`, `pin = generatePin()` (15 CSPRNG digits + Verhoeff), `pinKey = hmacKey(secret, 'pin', pin)`, `serial = giftId.slice(2,10)` → `GiftStore.create({ kind:'gift', state:'open', namehash, to, mb, pinKey, serial, payer, usd6, claimBy = now + 7 d })` with **`expiresIn = secondsUntil(claimBy)`** → receipt `gift` → HCS → `giftResponseSchema` (PIN once). Claim: `POST /challenge (path '/gift/claim')` → EIP-712 `GiftClaim { giftId, namehash, recipient, audience, nonce }` → `POST /gift/claim` → `consumeChallenge` → **R3** `GiftStore.openByNamehash` / `byPinKey` → `names.resolve` **again**, signer must equal the *currently* resolved address → `fulfil()` with `key = keys.entitlementGift(giftId)` → `markClaimed` → receipt `gift-claim` → HCS. Card: `GET /card/:serial` previews (read-only, constant-time 404); `POST /card/redeem { pin, challenge, sessionPubKey }` redeems (campaign-funded cards also `DataDrop.claim(campaignId, keccak(campaignId ‖ hmacKey(secret,'card',pin)))`). **Reclaim (D-7):** after `claimBy` the escrow entity is gone by protocol; `POST /gift/reclaim { giftId, payer, signature(GiftReclaim), challenge }` → `decideGiftReclaim({ escrow (expects null), receipts, ledgerOk, … })` → `'refund'` ⇒ pending `gift-reclaim` receipt → `treasury.refund({ to: payer, usd6 − fee })` (`TREASURY_PRIVATE_KEY`, `TREASURY_MAX_USD6_PER_DAY`) → patch tx → HCS. A ledger error is 503, never a refund.

**F4 — agent (`services/agent`).** Every `AGENT_TICK_MS`: **R2** `EntitlementStore.getByKey(key)` straight from the ledger + `AgentPolicyStore.get(key)` + `ReceiptStore.spentUsd6(sha256(key), 'agent-topup', dayBucket(now))` → `shouldTopUp(e, policy, spentTodayUsd6, now, stepPriceUsd6, lastExpiryBought)` (pure code) → on `buy`: `fetchWithPayment(GET /esim/topup)` with a `Payer` whose `choose()` accepts only `AGENT_PAYTO_ALLOWLIST` triples and `amount ≤ AGENT_MAX_USD6_PER_STEP`; local `EvmPayer` (Anvil #4), live `HederaPayer` (Agent Kit) + `EvmPayer` fallback → HCS `agent-topup` with the HCS-14 UAID (`X-Agent-Uaid` header on the request) → `AgentPolicyStore.put({ lastExpiryBought })` → `phraseNotification(facts, llm?)` from an allow-listed struct (T-55). Retry: keep the signed payload until `validBefore`; re-read the ledger before re-signing (T-57). Policy comes from `PUT /agent/policy` (EIP-712 `AgentPolicy`, D-10).

**F5 — usage reconciliation (`POST /webhooks/reseller/:provider`).** Raw body + provider headers (mock: `x-recharge-signature`, `x-recharge-timestamp`, `x-recharge-event-id`; **eSIM Access: no signature** — the route adds pseudo-headers `x-recharge-url-token` = `?token=` and `x-recharge-remote-ip`, stripping client-sent copies, A-27) → `reseller.verifyWebhook(rawBody, headers, now)` (pure; mock: MAC + skew ± 300 s; eSIM Access: constant-time token + sender-IP allow-list + body-hash replay cache; both hold their own replay cache) → for eSIM Access every event is a **hint**: `reseller.usage(iccid)` is re-read and *its* numbers are patched → `parseWebhook` → `usedMb` monotonic, `≤ totalMb` → `EntitlementStore.patch({ mbUsed, usageAsOf, usageSource:'webhook' })` → 204 / 401 / 409 / 400, never 500. Reseller = truth for **usage**, Arkiv = truth for **entitlement**.

**F6 — sponsor.** Wallet: `USDC.approve` → `DataDrop.createCampaign(id = keccak(sponsor ‖ name ‖ salt), …)` (token mode pulls USDC; `CampaignExists` protects the id). API: `POST /sponsor { campaign, auth: EIP-712 SponsorLogin }` → signer == `campaign.sponsor` == on-chain `campaigns(id).sponsor` → `CampaignStore.put` → returns `auditKey = HMAC(secret, 'audit' ‖ id)` **once**. `GET /sponsor/:id` (`Authorization: Recharge-Sponsor base64{sponsor, issuedAt, signature}`, 1 h) = chain counters + `ReceiptStore.forCampaign` (published `campaignClaimKey`s) + `EntitlementStore.expiringWithin(24 h)`. `pause`/`refund` are sponsor-wallet transactions; the API's anomaly rule calls `pause(id, true)` at ≥ 80 % of `claimsPerHour` in 10 min.

### 6.3 Expiry-clock skew — Arkiv `expiration` vs server time (T-35)

Arkiv's expiry is **block-based**: SDK 1.0.1 takes `{ expiration: ExpirationTime.fromSeconds(n) }` (n a whole number of 2-s blocks; also `fromMinutes/Hours/Days`, `atBlock`, `atDate`), stores `$expiresAt` as a **block number**, and reverts `ExpiryBeyondMaxLifetime` past 7,884,000 blocks (≈ 182.5 d). The port's `Ledger.put` keeps `expiresIn` in **seconds** (INTERFACES A-24) and the mock turns it into `createdAt + expiresIn × 1000`. `ArkivLedger` must map `seconds → ExpirationTime.fromSeconds(ceil(seconds / 2) × 2)`, refuse anything above the max lifetime before sending, and report back `expiresAt` derived from `$expiresAt` and the chain's own head (block timing via `getBlockTiming`). The three load-bearing reads (every `/esim/*` request, the agent's remaining-MB read, the gift claim) therefore see **the ledger's** clock, while the PWA countdown and the agent's `topUpOnExpiry` trigger see **the server's**. Attacks: (a) make the agent believe the plan expired (early ledger expiry) ⇒ it buys a top-up for a plan the reseller still serves (money wasted; bounded by the cap); (b) late ledger expiry ⇒ `/me/:key` shows MB the reseller has already cut off (support noise); (c) the agent loops on `expiry` because the entitlement's `expiresAt` never changes after a top-up that the reseller rejected.

**Controls:** `expiresAt` in every response is `LedgerPutResult.expiresAt`; annotations also carry `expiresAt`; readers use `min(ledgerAlive, annotations.expiresAt > now)`; the agent fires `expiry` once per distinct `expiresAt` value and only after a fresh ledger read; `ArkivLedger` logs `impliedDriftSec = |expiresIn − blocks × measuredBlockTimeSec|` and the Wednesday rabdi measurement goes into `docs/ARKIV_FEEDBACK.md`; entities are created with `flags.permissionlessExtension = false` (the default) so nobody else can extend an escrow past its claim window (T-79) with the 60-second-cache question. **Tests:** `wave1-adapters.md` L1–L3.

### 6.4 Rate-limit and hourly-cap races; the drain bound (T-01, T-02, T-45, T-46)

The sponsor-pool release is a self-attestation by our key — structural, not removable (DECISION §10, Security dissent). The design bounds it instead:

```
drain(1 h) ≤ Σ_{live campaigns c} min(budget_c − spent_c, pricePerClaim_c × claimsPerHour_c)
burst at a bucket edge ≤ 2 × pricePerClaim_c × claimsPerHour_c within a few seconds
time-to-stop = detect (≤ 2 min: anomaly auto-pause at 80 % of cap / 10 min) + pause tx (≤ 1 min) + rotate (≤ 2 min)
```

Example demo campaign (`pricePerClaim = $0.50`, `claimsPerHour = 100`, budget $500): worst hour $50, worst burst $100, worst day before anyone notices ≈ the budget. The sponsor keeps the pause key and the HMAC'd claim list, so the loss is auditable and refundable (`refund` after a 24 h pause). The **API-side** cap is a convenience (saves gas and burned verifications — T-24/T-46); the **contract** is the control. The red team tests both and the race between them.

### 6.5 LPA secrecy (T-31, T-32, T-60, T-61, T-62)

An LPA string is a bearer secret: whoever installs it first owns the plan. Its lifecycle must be: reseller → API handler memory → `sealLpa` → sealed blob in the entity / returned once → `openLpa` in the PWA (memory) → Apple universal link / Android intent → gone. Specifically forbidden: the LPA or the sealed blob in logs or in `localStorage`; the LPA in any ledger payload, annotation, HCS message, error message, analytics event, URL of ours, or the inventory file in clear; a second delivery (the second `GET /me/:key` omits `sealedLpa`; a second fetch of a dedicated `/esim/lpa/:token` returns 410); the QR without an explicit tap; a service-worker cache of any API response. The universal link necessarily carries the LPA in its query string — that is Apple's design — so the page that opens it sends `Referrer-Policy: no-referrer`, uses `rel="noreferrer"`, and never routes through a third-party redirector. **Screenshots** are a user choice; the UI says so once, next to the QR. The PWA keeps the *opened* LPA in IndexedDB only until the install is confirmed (T-76), because iOS needs the universal link to be re-openable after a Settings round-trip.

### 6.6 Webhook HMAC windows (T-34, T-40)

`verifyWebhookSignature(secret, rawBody, signature, timestamp, now, windowSec = 300)` — the MAC covers `${timestamp}.${rawBody}` over the **raw** bytes Hono gives via `c.req.text()` (never a re-serialised object; key order and whitespace would change the digest); `timestamp` is seconds; `|now − timestamp| ≤ 300` in **both** directions (a webhook "from the future" is as suspicious as a stale one); `timingSafeEqual` over equal-length buffers (length mismatch ⇒ `false` without comparing); a replay cache keyed by `sha256(signature)` with a 5-minute TTL; each reseller has its own scheme and header names — the adapter's `verifyWebhook` normalises; the fixtures record the exact headers. **eSIM Access publishes no webhook signature** (API-FACTS §5.1, A-27): its `verifyWebhook` checks a constant-time URL token (`ESIMACCESS_WEBHOOK_TOKEN`, ≥ 32 random bytes, delivered as `x-recharge-url-token` by the route, which strips any client-sent copy), the documented sender IPs (`3.1.131.226, 54.254.74.88, 18.136.190.97, 18.136.60.197, 18.136.19.137`; `X-Forwarded-For` honoured only with `TRUST_PROXY=1`), and a body-hash replay cache — and the route treats every event as a hint, re-reading `reseller.usage(iccid)` (`/esim/query`) and patching *those* numbers (T-82); `usedMb` is monotonic per ICCID and `usedMb ≤ totalMb`; an unknown ICCID returns `204` (do not confirm existence) and logs a warning. Route behaviour: valid ⇒ `204`; bad signature or skew ⇒ `401`; replay ⇒ `409`; malformed ⇒ `400`; never `500`.

### 6.7 Key rotation and pause drill (T-01, T-10; DECISION §6.5 right-hand column, §6.7 Fri)

**Trigger:** claim rate ≥ 80 % of `claimsPerHour` in any 10-minute window, claims while PWA traffic is zero, a `Claimed` event whose `claimKey` is not in the API's own log, or any suspicion the VPS is compromised. **Target: < 5 minutes from trigger to "new attestor live", measured Friday 6 Nov and recorded in `security/redteam/findings/DRILL-attestor-rotation.md`.**

1. **Pause (≤ 1 min).** `pnpm --filter @ethglobal/api drill:pause-all` (a `scripts/redteam/pause-all.ts` built on `scripts/lib/harness.ts`) → the API's attestor signer calls `pause(id, true)` for every live campaign (an attacker who holds the same key can also pause — that only helps). The sponsor can do the same from `/sponsor` with their own wallet. Verify `Paused(id, true, by)` events on HashScan.
2. **Rotate (≤ 2 min).** On-site, generate a new ECDSA key (never on the VPS, never pasted into an AI context); owner (cold key) calls `setAttestor(newAttestor)`; `AttestorSet` event verified; update `ATTESTOR_PRIVATE_KEY` in the VPS env (`env.ts` refuses Anvil keys in live); `systemctl restart recharge-api`; `GET /healthz` must report `attestor: <new address>` — `healthSchema` (INTERFACES §1.6) does not have this field yet; §7 asks for it.
3. **Unpause (sponsor only).** The attestor cannot unpause by design; the sponsor (or the teammate acting as the demo sponsor) sends `pause(id, false)`.
4. **Audit (≤ 10 min, not on the clock).** Publish the HMAC'd claim list for the window from `/sponsor/:id`; reconcile against `Claimed` events; compute drained amount; refund path if needed.
5. **Rehearsal in local mode (wave 1):** the same four steps against Anvil are a Foundry test (`wave1-contracts.md` A18) and an `e2e-local.sh` scenario; the Friday drill repeats them on Hedera testnet.

Related rotations: **`OCTROI_SECRET`** — never rotated during a campaign (T-29); **webhook secrets** — rotate at the reseller dashboard, dual-accept old+new for 10 minutes; **relayer key** — rotate by replacing the env and sweeping the float; **agent wallet** — the user revokes by pausing the policy (`/agent` sheet) and moving funds.

### 6.8 PWA: XSS, CSRF, clickjacking, headers (T-47, T-54, T-58–T-64)

The PWA holds no session cookie, so CSRF reduces to "no state change on GET" (T-47) and a CORS allow-list. The real risks are XSS (sponsor names, gift messages, plan names, 402 `error` strings, ENS avatars), clickjacking of the two consent sheets (pay; agent cap), and leakage of the LPA through browser plumbing. Required headers from `next.config.ts` `headers()` on every route: `Content-Security-Policy` (see T-58; wallet connectors may need `'wasm-unsafe-eval'` and a `connect-src` list of RPC/facilitator hosts — keep it explicit), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Permissions-Policy: camera=(self)` (IDKit/QR scanning only where needed), `Cache-Control: no-store` on anything that can contain an entitlement. The service worker caches the shell and fonts only. `dangerouslySetInnerHTML` and `eval` are lint failures. The demo wallet panel is compiled out of live builds (T-63).

### 6.9 Dependencies and supply chain (T-65–T-67)

New in `v0` (exact versions from API-FACTS / INTERFACES A-19…A-25): `@noble/ciphers`, `@noble/curves`, `@noble/hashes`, `viem` (present), `hono` (present), `zod` (present), `@arkiv-network/sdk@1.0.1`, `@hiero-ledger/sdk@2.90.1` (one copy, via `@x402/hedera` re-exports — `pnpm why @hiero-ledger/sdk` shows one), `@x402/{core,evm,hedera,fetch,hono}@2.29.0`, `@hashgraph/hedera-agent-kit@4.2.0`, `@worldcoin/idkit@4.6.0` + `@worldcoin/idkit-core@4.6.0`, `@hashgraphonline/standards-sdk@0.1.192` (HCS-14 conformance), Playwright. Banned look-alikes: `@hashgraph/sdk`, unscoped `hedera-agent-kit`, `golem-base-sdk`, `@worldcoin/idkit-standalone`, the v1 `x402`/`x402-*` packages (semgrep `recharge-*-legacy-primitive`). Controls: frozen lockfile (CI), `pnpm audit --prod` in CI (`security/redteam/tools/deps-check.sh`), `minimumReleaseAge` in `pnpm-workspace.yaml`, no new entries in `onlyBuiltDependencies` without a finding, exact-version pins for sponsor SDKs, package names confirmed against the sponsor docs by a human at the Wednesday pre-deploy (the sandbox cannot open those docs), Foundry libs pinned, and no `npx <unpinned>` in `scripts/`. The orchestrator's own context is a supply chain too: **no private key, API key or webhook secret ever enters an AI context** (DECISION §7.3) — `.env` is git-ignored and the red team greps the repo for key-shaped strings in every wave.

### 6.10 AI-policy risk — prompt injection (T-55, T-70)

The only LLM in the product phrases notifications ("Your agent bought 100 MB for $0.40 — 220 MB left, expires Sunday"). Everything it could be asked to read is attacker-influenced somewhere: campaign `name` (sponsor), plan name (reseller), gift message (any payer), ENS text records (name owner), reseller error strings. The rule is architectural, not a filter: the decision path (`shouldTopUp` → signer) imports nothing from the inference adapter (enforced by an eslint `no-restricted-imports` rule in `services/agent`), the LLM receives a typed object with numbers and enums only, and its output is text rendered escaped. The canary test (DECISION §6.5 agent row) plants an instruction in the entitlement payload and asserts purchases and policy are unchanged. If AgentKit's discount mode lands and an "agent lane" talks to World, the same boundary applies: the credential changes the **price**, never the **policy**. The same rule covers the Hedera Agent Kit (T-84): its LangChain/AI-SDK/MCP toolkits hand transfer tools to a model and are banned in `services/agent`; the kit is called from code only (`HederaAgentAPI.run` with computed arguments).

### 6.11 Regulator-as-adversary and data minimisation (T-37, T-52, T-68, T-69)

Public chains and Arkiv are evidence. The product's legal posture (no sale in India; zero-price gifts to non-residents; testnet paid lane in the demo; mainnet only outside India after the memo) must be true **in the configuration**, not only in the pitch: `accepts[]` is testnet-only until two explicit flags are set; no entity, event or receipt contains PII, an ICCID in clear, a raw nullifier, or a payer↔human link; verification logs are hashed and short-lived; the inventory file is encrypted; the sponsor dashboard shows HMAC'd keys. A subpoena then yields what the pitch already says.
